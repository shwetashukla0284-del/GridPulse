## Phase 3 — Step 1: Broadcast readings over batched WebSockets

- **Built:** Added a WebSocket endpoint at `/ws/readings`, a connection hub, and a background batcher. The Redis consumer writes each valid reading to TimescaleDB first, then enqueues it for live delivery. The bounded queue has capacity 1,000; overflow discards and counts the oldest live update. The batcher flushes after 100 ms or 100 readings, whichever comes first.
- **Concepts learned:** A WebSocket is a persistent, bidirectional connection, unlike short-lived HTTP requests. Batching sends multiple readings in one event to reduce per-message overhead. Slow or disconnected clients are removed after a send error or one-second timeout.
- **Key decisions:** Persist before live fan-out so a WebSocket queue overflow does not discard the database record. Broadcast each batch concurrently to connected clients. Keep the queue and hub process-local for this single-instance learning setup; multiple API workers would need a shared fan-out layer.

## Phase 6 — Step 1: Rolling z-score anomaly detector and evaluation

- **Built:** `backend/app/anomaly.py` defines `RollingZScoreDetector`: per-meter rolling window of the last 30 demand values, z = (value − mean) / std, flag when |z| > 3, a 10-sample warm-up, and a 0.05 kW std floor. A `baseline_policy` controls how flagged values enter the window (`clip`, `exclude`, `include`). `tests/evaluate_anomaly.py` (`python -m tests.evaluate_anomaly`) scores the detector against the simulator's injected faults. Not yet wired into the live pipeline.
- **Concepts learned:** A z-score measures how many standard deviations a value sits from a baseline. A rolling, per-meter baseline adapts to the daily curve and to each household. Precision = flagged readings that were real faults; recall = real faults that were flagged; false-positive rate = normal readings wrongly flagged. The detector must not read `is_fault`; it is only the answer key. How flagged values feed back into the baseline matters as much as the threshold.
- **Key decisions:** Default `baseline_policy="clip"` (winsorizing: a flagged value enters the window capped at mean ± threshold·std), chosen from measurements below rather than assumption. Keep the threshold at 3.0 for now; tuning should be checked on a different seed than the one used to choose it.
- **Problems and fixes:** (1) The first version used `exclude` as the default, assuming it protects the baseline. The evaluation showed 1,412 false positives at threshold 3.0. Diagnosis took three hypotheses: a frozen baseline (rejected: false-positive runs were at most 2 readings long); std shrinkage to the floor (rejected: median std 0.094 vs 0.099 kW, never at the floor); one-sided exclusion during a trend (confirmed: false positives clustered 00:00–03:00, during the post-evening-peak decline, and 1,193 of 1,412 were *below* baseline — dropped lows keep the mean too high, which flags the next ordinary low). (2) A unit test expected `include` to miss the second surge; measured z-scores were 48.7 → 4.2 → missed from the third, so the test now asserts that. (3) A synthetic linear-trend test flagged nothing under any policy because the slope inflates the window std; replaced with a seeded simulator night run (20:00–03:00), where `exclude` gave 188–339 false positives vs 12–21 for `clip` across seeds 1–3.
- **Verification:** 37 unit tests passed (8 detector tests). Evaluation on 5 meters × 3 days at 1-minute intervals (21,600 readings, 229 injected faults, seed 2026):

- **Built:** The Redis consumer now runs each saved reading through `RollingZScoreDetector`; alerts are stored in a new `anomaly_alerts` hypertable, counted in `/health` (`anomalies_detected`), queued after their reading, and broadcast as an added `alerts` array on the existing WebSocket `readings` message. - **Concepts learned:** Stateful stream processing: the detector keeps per-meter memory in the API process, so a restart clears it and each meter needs a 10-reading warm-up. Held-out validation: choose a setting on one dataset and confirm it on data not used for the choice.
- **Key decisions:** Threshold 4.0, chosen on seed 2026 and confirmed on held-out seeds. Persist reading → detect → persist alert → enqueue reading then alert, so the database is the complete record. Alerts use `ON CONFLICT DO NOTHING`: a replay is judged against a different in-memory baseline, so the first judgement is kept. ## Phase 7 — Step 2: Load test for throughput and end-to-end latency

- **Built:** `tests/load_test.py` (`python -m tests.load_test --api http://127.0.0.1:8001 --rates 25 50 100 200`) publishes readings to Redis at fixed rates for 10 s per stage and listens on `/ws/readings` in the same process, so send and receive times share one clock. It reports achieved publish rate, delivered throughput, delivered/published, rows persisted (from `/readings/count`), live-queue drops (from `/health`), and nearest-rank p50/p95/p99/max latency (publish call → WebSocket receipt). It waits for the server to consume each stage before the next so backlogs do not overlap. Added a `READINGS_CHANNEL` environment variable to the API so the test runs on `gridpulse:loadtest`, isolated from the outdated API still running on port 8000. Test rows use `load-` meter IDs and 2030+ timestamps.
- **Concepts learned:** Throughput (readings per second delivered) and latency (time for one reading) are different measures. Percentiles describe the tail users feel; p95 = 95% of readings were at least this fast. Past capacity, a queue builds and latency grows with run length rather than staying constant. A commit waits for the write-ahead log to be flushed to disk (fsync) unless `synchronous_commit` is off. A sequential consumer's maximum rate is about 1 / (time per message).
- **Key decisions:** Report ranges from two full runs instead of one number because this machine's results varied heavily. Test 25–200/s after a smoke run showed capacity far below the initially planned 100–2000/s. Keep the 9,905 load-test rows (identifiable by `meter_id LIKE 'load-%'`) until the user decides whether to delete them.
- **Problems and fixes (diagnosis):** (1) A 100/s smoke run showed ~3.1 s latency with a narrow spread, which looked like a fixed delay. A single-message probe measured ~135 ms (100 ms batch window + ~35 ms), ruling out a fixed delay. (2) A timeline trace crashed on an index error in the probe script itself (it assumed every reading arrived) and was fixed; the rerun showed the server consuming about 1 reading/s and still delivering the previous run's backlog. (3) API CPU was ~15% of one core during load and the database showed idle connections, so the server was waiting, not computing. (4) Timing the same `INSERT` from Windows without the API: 5/s with p95 556 ms in one run, but 134/s (median 5.6 ms) minutes later; with `synchronous_commit=off` for that test session only, 298/s (median 3.0 ms). Conclusion: throughput is bounded by sequential per-reading commits, and commit latency on this machine (Docker Desktop WSL 2 virtual disk on a SATA SSD, shared with other applications) varies widely. The ~1/s period matches a disk stall, but its exact cause was not proven. (5) One Python test run after the load test reported an error that did not reproduce in 8 subsequent runs; the traceback was not captured, so the failing test is unknown.
- **Verification (measured; Intel Core i3-6006U 2 cores / 4 threads, 7.9 GB RAM, Windows 10, Docker Desktop with WSL 2; client, API, Redis, and TimescaleDB all on this one laptop; 10 meters, 10 s per stage; two runs):**

  | 50 | 50 | 500/500 | 500 | 0 | 80–91 | 156–315 | 283–417 | 365–482 |

  Sustainable rate on this machine was about 65–76 readings/s; at ≤ 50/s, p50 stayed under 100 ms (mostly the 100 ms batching window). ## Phase 7 — Step 3: Batch database writes and re-measure

- **Built:** The consumer now uses natural batching. A reader task moves Redis messages into a bounded inbox (4 × batch size; when full, the reader waits, so a backlog stays in Redis). The consumer waits for one message, takes any others already waiting (up to `CONSUMER_MAX_BATCH`, default 500), validates and runs the detector on each, then saves all readings and alerts with `executemany` inside one transaction (`PostgresReadingRepository.save_batch`, replacing `save_reading`/`save_alert`). Live events are queued after the commit in publish order. `/health` reports `batches_saved` and `largest_batch`. A Redis reader failure now propagates and stops the consumer.
- **Concepts learned:** Natural batching takes what is already waiting instead of waiting for more (a linger timer), so batches stay tiny at low load (no added latency) and grow under load, sharing one commit/fsync across many rows. A bounded buffer between stages applies backpressure upstream instead of growing memory. A fair A/B comparison runs both versions back to back, alternating, on the same machine state.
- **Key decisions:** `executemany` in a transaction rather than a single multi-row `INSERT ... unnest(...)`, which would fail on a duplicate key within one batch (a replay), or `COPY`, which cannot upsert. Detection runs before the commit and alerts are saved in the same transaction as their readings, so a reading and its alert are stored atomically. `CONSUMER_MAX_BATCH=1` reproduces the previous one-commit-per-reading behavior for comparisons.
- **Problems and fixes:** None in the implementation; all 43 Python tests passed on the first run. Measurement caveat: at the 400/s target the load-test client itself reached only 277–388 published/s, so the batched consumer's ceiling was not reached.
- **Verification:** 43 Python tests passed (new: waiting messages saved together up to the limit with publish order preserved; batch size 1 saves individually; Redis reader failure stops the consumer; invalid batch size rejected). A/B load test, same laptop and method as Phase 7 step 2, alternating `CONSUMER_MAX_BATCH=1` and `500` for two rounds, 10 s per stage, fresh API on port 8001 each time:

  | offered/s | batch=1 delivered/s | batch=1 p50 / p95 ms | batch=500 delivered/s | batch=500 p50 / p95 ms |
